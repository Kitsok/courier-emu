Task: Move practical peripheral emulation from Python into native C++
Status: In progress; evaluating a reusable native CPU backend

Inventory the analog Courier's remaining Python peripheral implementation
and move as much as practical into the native C++ runtime. Python should
retain configuration, orchestration, diagnostics, and a reference path;
per-byte, per-sample, and interrupt-sensitive device work should run natively.

Prioritize:
1. The 80C186 UART: registers, RX/TX buffers, status, handshake signals,
   interrupt request generation, and character timing.
2. The DTE wire/autobaud model and admission of terminal bytes into the UART.
3. Parallel I/O and peripheral-register callbacks, including the DSP reset
   pins, serial input, EEPROM signals, and board latch wiring.
4. Remaining timer/controller access glue and memory-map/register routing
   where migration removes frequent Python callbacks.

Build on shared native device state and the native IRQ controller. Avoid
duplicating authoritative state or moving host configuration work merely
because it is written in Python. Document any device behavior that remains
in Python, or is only a placeholder rather than a complete hardware model.

Acceptance criteria:
- Audit and document the ownership boundary for each relevant peripheral.
- Migrate and validate devices in separate logical changes with focused
  register, timing, interrupt, and native/reference comparison tests.
- Preserve firmware-driven behavior, interrupt masks, pending requests,
  priority, interrupt shadows, and exactly-once EOI processing.
- Verify boot, AT commands, escape handling, AT&T1, and sustained data with
  error correction required (&M5). Use fresh temporary NVRAM and retain
  existing persistent settings. Do not force CONNECT or assist acquisition.
- Measure callback counts and host CPU/throughput before and after each
  migration; distinguish idle, training, and sustained connected workloads.
- Record remaining high-speed link errors separately from scheduler fixes.

This follow-up is separate from the current IRQ starvation investigation.

Milestone 1 complete: native integrated-UART state and device operations.
Registers, RX holding state, TX accounting and request generation now use
C++ state with Python inspection views and the shared native IRQ latches.
Register routing, host output and DTE wire/admission remain in Python.
COURIER_NATIVE_UART=0 retains the Python device for comparison.

Milestone 2 complete: native CPU access to the integrated-UART registers.
After the initial MMIO trace fills, register reads/writes and their UART
side effects stay in C++. Status reads are transactional across instruction
guard failures; extra observers keep synchronous callbacks. Host TX output
is drained before the next instruction/poll. Native access counts appear
in scheduler diagnostics; COURIER_NATIVE_UART_MMIO=0 retains Python routing.

Remaining ownership boundary:
- Python: DTE input queue, wire frame timing, byte admission, command-mode
  adapter and host terminal output/transport.
- Python: parallel-port board wiring, EEPROM pin protocol, DSP reset/NMI
  transitions and remaining MMIO routing.
- Native: integrated-UART register/RX state, TX accounting/request latches,
  eligible CPU register accesses and shared interrupt arbitration/entry.
- Native timers retain their existing shared-state implementation; their
  board callbacks and some register access paths still use Python.

Milestone 3 complete: native DTE input-wire model.
Frame state, bit sampling, start-edge consumption and character completion
now execute in C++. Python retains a live inspection view and orchestration;
COURIER_NATIVE_DTE=0 selects the reference wire. This supersedes the earlier
ownership entry for wire timing; byte admission and autobaud adaptation are
not yet migrated.

Expanded target requested by the user: move host terminal transport and
runtime CPU fallback into C++ too. A Python reference interpreter may only
remain as a development tool, not as a runtime dependency.

Architecture audit and reason for pausing:
- runtime.py launches a Python machine; build.py builds a CPython extension
  and native DSP library, not a standalone 80186 modem executable.
- x86_interpreter.cpp deliberately exits on watched memory, unhandled I/O
  and unsupported instructions. x86_interpreter.py owns their fallback,
  including Python memory/I/O callbacks and remaining instruction handling.
- machine.py owns firmware boot/mapping, board callbacks, DTE admission and
  firmware callback adaptation. console.py owns terminal input/output and
  pending-output/error handling.
- The native c5x_runner.cpp executable is a DSP runner, not a modem machine.

The standalone target is feasible, but removing Python fallback requires
an owning native machine/bus layer first. Thin C API wrappers around more
Python callbacks would not satisfy the expanded target. The next milestone
must extract a host-independent CPU interface with structured exit reasons,
then provide native bus/device dispatch and a C++ slow instruction path.
After that, move board boot, DTE admission, terminal transport and runtime
control to the native owner before switching the production launcher.
This is an architectural prerequisite rather than a peripheral algorithm
that cannot be expressed in C++; no claim of a fully native runtime is made.

Milestone 4 complete: experimental MAME CPU-to-Courier board adapter.
The user approved evaluating reuse before extending the custom CPU. A
pinned BSD-3-Clause MAME 80186 core and standalone compatibility layer now
execute instructions against the existing Courier memory/I/O callbacks.
The shim's optional address-space bounds bug is corrected. There is no
Python instruction-decoder fallback in this backend. Select it with
COURIER_X86_BACKEND=mame after explicitly building that optional backend.

Observed validation: fresh-NVRAM analog403 boot, matching DSP download, and
AT/ATE0&M5/ATI4/ATI5 responses passed. Focused checks cover word-wide bus
access, I/O timestamps, clock stop/resume, watched-code stops, stable backing
buffers and interrupt/fault notifications. No AT&T1 or data-rate claim is
made for MAME. Python still owns the board callbacks, IRQ dispatch and host
transport; the custom native CPU's worker/IRQ batching ABI is not enabled.

The earlier custom-core extraction proposal is superseded for now by this
reuse evaluation. Next compare firmware IRQ/data behavior with the existing
backend, then migrate the board/bus and host transport around the reused
CPU. A complete standalone native modem has not yet been delivered.

Milestone 5 complete: remove MAME's UART/IRQ/DSP-port Python hot paths.
The MAME adapter now uses existing native device buffers and native DSP port
handlers directly. IRQ requests enter at eligible instruction boundaries,
with MAME's interrupt shadow; EOI and UART writes are committed once, and
host output is drained before the CPU resumes. Extra UART observers retain
synchronous callbacks. No new firmware tracing or diagnostic hooks were
introduced. The custom CPU's worker batching ABI remains disabled.

Observed focused performance: 40,000 status reads went from 40,000 Python
UART callbacks to zero (about 61 ms to 2.7 ms CPU in one local comparison).
This is a register-loop measurement, not an end-to-end modem speed claim.
Six focused adapter checks and the fresh-NVRAM AT/OK smoke passed. Timer
register paths, remaining board wiring and host transport still need work.
