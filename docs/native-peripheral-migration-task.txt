Task: Move practical peripheral emulation from Python into native C++
Status: In progress; MAME is the configuration-driven runtime default

Inventory the analog Courier's remaining Python peripheral implementation
and move as much as practical into the native C++ runtime. Python should
retain configuration, orchestration, diagnostics, and a reference path;
per-byte, per-sample, and interrupt-sensitive device work should run natively.

Prioritize:
1. The 80C186 UART: registers, RX/TX buffers, status, handshake signals,
   interrupt request generation, and character timing.
2. The DTE wire/autobaud model and admission of terminal bytes into the UART.
3. Parallel I/O and peripheral-register callbacks, including the DSP reset
   pins, serial input, EEPROM signals, and board latch wiring.
4. Remaining timer/controller access glue and memory-map/register routing
   where migration removes frequent Python callbacks.

Build on shared native device state and the native IRQ controller. Avoid
duplicating authoritative state or moving host configuration work merely
because it is written in Python. Document any device behavior that remains
in Python, or is only a placeholder rather than a complete hardware model.

Acceptance criteria:
- Audit and document the ownership boundary for each relevant peripheral.
- Migrate and validate devices in separate logical changes with focused
  register, timing, interrupt, and native/reference comparison tests.
- Preserve firmware-driven behavior, interrupt masks, pending requests,
  priority, interrupt shadows, and exactly-once EOI processing.
- Verify boot, AT commands, escape handling, AT&T1, and sustained data with
  error correction required (&M5). Use fresh temporary NVRAM and retain
  existing persistent settings. Do not force CONNECT or assist acquisition.
- Measure callback counts and host CPU/throughput before and after each
  migration; distinguish idle, training, and sustained connected workloads.
- Record remaining high-speed link errors separately from scheduler fixes.

This follow-up is separate from the current IRQ starvation investigation.

Milestone 1 complete: native integrated-UART state and device operations.
Registers, RX holding state, TX accounting and request generation now use
C++ state with Python inspection views and the shared native IRQ latches.
Register routing, host output and DTE wire/admission remain in Python.
COURIER_NATIVE_UART=0 retains the Python device for comparison.

Milestone 2 complete: native CPU access to the integrated-UART registers.
After the initial MMIO trace fills, register reads/writes and their UART
side effects stay in C++. Status reads are transactional across instruction
guard failures; extra observers keep synchronous callbacks. Host TX output
is drained before the next instruction/poll. Native access counts appear
in scheduler diagnostics; COURIER_NATIVE_UART_MMIO=0 retains Python routing.

Remaining ownership boundary:
- Python: DTE input queue, wire frame timing, byte admission, command-mode
  adapter and host terminal output/transport.
- Python: parallel-port board wiring, EEPROM pin protocol, DSP reset/NMI
  transitions and remaining MMIO routing.
- Native: integrated-UART register/RX state, TX accounting/request latches,
  eligible CPU register accesses and shared interrupt arbitration/entry.
- Native timers retain their existing shared-state implementation; their
  board callbacks and some register access paths still use Python.

Milestone 3 complete: native DTE input-wire model.
Frame state, bit sampling, start-edge consumption and character completion
now execute in C++. Python retains a live inspection view and orchestration;
COURIER_NATIVE_DTE=0 selects the reference wire. This supersedes the earlier
ownership entry for wire timing; byte admission and autobaud adaptation are
not yet migrated.

Expanded target requested by the user: move host terminal transport and
runtime CPU fallback into C++ too. A Python reference interpreter may only
remain as a development tool, not as a runtime dependency.

Architecture audit and reason for pausing:
- runtime.py launches a Python machine; build.py builds a CPython extension
  and native DSP library, not a standalone 80186 modem executable.
- x86_interpreter.cpp deliberately exits on watched memory, unhandled I/O
  and unsupported instructions. x86_interpreter.py owns their fallback,
  including Python memory/I/O callbacks and remaining instruction handling.
- machine.py owns firmware boot/mapping, board callbacks, DTE admission and
  firmware callback adaptation. console.py owns terminal input/output and
  pending-output/error handling.
- The native c5x_runner.cpp executable is a DSP runner, not a modem machine.

The standalone target is feasible, but removing Python fallback requires
an owning native machine/bus layer first. Thin C API wrappers around more
Python callbacks would not satisfy the expanded target. The next milestone
must extract a host-independent CPU interface with structured exit reasons,
then provide native bus/device dispatch and a C++ slow instruction path.
After that, move board boot, DTE admission, terminal transport and runtime
control to the native owner before switching the production launcher.
This is an architectural prerequisite rather than a peripheral algorithm
that cannot be expressed in C++; no claim of a fully native runtime is made.

Milestone 4 complete: experimental MAME CPU-to-Courier board adapter.
The user approved evaluating reuse before extending the custom CPU. A
pinned BSD-3-Clause MAME 80186 core and standalone compatibility layer now
execute instructions against the existing Courier memory/I/O callbacks.
The shim's optional address-space bounds bug is corrected. There is no
Python instruction-decoder fallback in this backend. Select it with
COURIER_X86_BACKEND=mame after explicitly building that optional backend.

Observed validation: fresh-NVRAM analog403 boot, matching DSP download, and
AT/ATE0&M5/ATI4/ATI5 responses passed. Focused checks cover word-wide bus
access, I/O timestamps, clock stop/resume, watched-code stops, stable backing
buffers and interrupt/fault notifications. No AT&T1 or data-rate claim is
made for MAME. Python still owns the board callbacks, IRQ dispatch and host
transport; the custom native CPU's worker/IRQ batching ABI is not enabled.

The earlier custom-core extraction proposal is superseded for now by this
reuse evaluation. Next compare firmware IRQ/data behavior with the existing
backend, then migrate the board/bus and host transport around the reused
CPU. A complete standalone native modem has not yet been delivered.

Milestone 5 complete: remove MAME's UART/IRQ/DSP-port Python hot paths.
The MAME adapter now uses existing native device buffers and native DSP port
handlers directly. IRQ requests enter at eligible instruction boundaries,
with MAME's interrupt shadow; EOI and UART writes are committed once, and
host output is drained before the CPU resumes. Extra UART observers retain
synchronous callbacks. No new firmware tracing or diagnostic hooks were
introduced. The custom CPU's worker batching ABI remains disabled.

Observed focused performance: 40,000 status reads went from 40,000 Python
UART callbacks to zero (about 61 ms to 2.7 ms CPU in one local comparison).
This is a register-loop measurement, not an end-to-end modem speed claim.
Six focused adapter checks and the fresh-NVRAM AT/OK smoke passed. Timer
register paths, remaining board wiring and host transport still need work.

Milestone 6 complete: MAME native timer/controller register fast paths.
Ordinary count, compare and control reads and timer/controller writes now
operate on shared native state without Python callbacks. Delay acceleration
and timer-0 board-clock selection retain their existing slow paths. Existing
access totals are folded by batch; extra memory observers remain synchronous.

Observed: 40,000 timer reads produced matching register/timer state while
removing all Python callbacks (about 95 ms to 2.3 ms in one local comparison).
Seven focused adapter checks passed. A 15-second AT&T1 run at 24,000 bit/s
with required LAPM returned 6,016 exact bytes, escaped successfully, and
reported zero block errors, resends or timeouts. No additional firmware
probes or debugging interfaces were added.

Milestone 7 complete: native terminal byte transport for MAME's plain PTY.
Nonblocking reads/writes, bounded pending output, EOF/error handling, waiting,
lamp writes and descriptor closure now execute in C++. Python retains the
existing console interface and live counter views. Existing objects are
adopted in place to retain descriptor ownership. Serialsim/custom console
subclasses keep their existing control-aware implementations.

Four focused reference/native checks cover bidirectional bytes, EOF,
accounting and bounded output with a stalled reader. Fresh-NVRAM AT/OK and
matching DSP download passed. Empty polling was approximately unchanged in
a small comparison; no transport speedup is claimed. The native transport
is reusable by a future native machine owner without Python byte-I/O code.

Milestone 8 complete: native EEPROM protocol and parallel-port hot path.
The existing Microwire command/read/write/erase state machine now runs in
C++, with in-place Python inspection/persistence views. MAME handles ordinary
parallel register accesses, EEPROM clocks and serial/EEPROM input pin samples
natively when the external DSP pins do not change. DSP reset/INT1/NMI edges
and writes while reset is held retain the existing board handler, preserving
its reset/download side effects. Existing access accounting is retained.

Two focused checks matched the reference EEPROM protocol and verified that
native clock traffic bypasses Python while a DSP reset edge still reaches
the board. Fresh temporary-NVRAM boot, AT commands, DSP download and AT&W
save passed. No additional firmware tracing/debug interfaces were added.

Milestone 9 complete: MAME is the configuration-driven analog runtime default.
The default build includes the MAME core; packaged builds ship its prebuilt
library and BSD license/provenance/notices. Runtime startup verifies it before
launch. COURIER_X86_BACKEND=native retains the previous CPU path. Legacy CLI
and direct reference/CPU APIs retain their prior defaults for comparison.

The staged-package check passed without native sources or a compiler on PATH:
configuration checking, default-MAME AT/OK, normal shutdown and ABI mismatch
handling were verified. This does not claim a fully standalone native modem.
Remaining work includes cycle-based scheduling/native ownership of board
services, the DTE admission/firmware adapter, rare DSP pin/reset callbacks,
and serialsim control-aware transport. Existing timer delay/clock callbacks
also retain their current slow paths. Unused peripheral features have not
been added solely for completeness; current work prioritizes hot paths.


Milestone 10 complete: reuse native board-service batching with MAME.
The existing board worker now services eligible instruction-clock deadlines
inside the MAME batch. Timer/DSP/media/idle-console handling retains its
existing guards and yields for Python-owned events. Native service state is
published before remaining Python device handlers run. MAME's shared IRQ
arbiter still owns delivery and respects the CPU's interrupt shadow. The
custom decoder/diagnostic-store trace ABI remains disabled for this backend.
COURIER_WORKER_POLL=0 retains Python service scheduling for comparison.

The two focused handoff cases use the actual native worker and verify both
elided periodic services and publication before a watched memory handler.
A one-million-instruction microbenchmark reduced Python service callbacks
from 976 to 4 (972 native services) with matching AX; median CPU time over
five local runs fell from 12.49 ms to 10.71 ms. This measures service-loop
overhead, not end-to-end modem throughput. No new debugging interfaces or
firmware probes were added. Python still owns startup, remaining board
callbacks, scheduled external events and control-aware host orchestration;
cycle-based timing and a standalone native application remain future work.

The final short AT&T1 check passed at 24,000 bit/s with required LAPM:
6,016 exact bytes over 15 seconds, working escape handling, zero lost
characters, block errors, resends and timeouts. Existing reporting counted
15,268 native service intervals. Full-modem CPU time was approximately
unchanged against the preceding milestone; no overall speedup is claimed.


Milestone 11 complete: native analog DTE receive queue and admission.
C++ owns queued bytes, firmware-readiness and command-state checks, the
existing attention/autobaud adapter updates, character start/completion,
ISR selection and UART delivery. Python exposes live adapter fields and
retains echo, command observation and service-call orchestration. Unknown
ROM layouts and other backends retain their existing receive path.

A focused current-change check passed admission, frame timing, queue order,
pending-IRQ gating and preservation of online ISR selection. A ten-second
AT&T1 check with &M5 and a 24,000-bit/s cap echoed 4,042 exact bytes and
escaped successfully. No additional firmware probes were introduced.


Milestone 12 complete: native UART-to-terminal transmit path.
Native UART writes feed bounded serial capture, result/mode recognition and
the existing terminal buffer directly. Terminal writes drain at service,
callback and batch boundaries. Individual transmitted bytes no longer end
a CPU batch or replay through Python serial processing. Access accounting
is folded by batch. Result lines and mode/scheduled-input events retain
their existing host behavior; control-aware serialsim stays on its prior
path. Live machine views expose online state and captured output.

Thirteen existing MAME/terminal checks passed. A focused current-change
check verified native guest UART output reaches the terminal in order,
preserves binary bytes, detects CONNECT and keeps access totals without
Python UART callbacks. A ten-second &M5 AT&T1 run at 24,000 bit/s echoed
3,995 exact bytes and escaped successfully. No new probes were added.


Milestone 13 complete: persistent native CPU/memory/device context.
The C++ context allocates and owns the RAM, access-guard and shared-register
buffers. Python uses live views. Native device buffer exports are retained
until the device set changes, and unchanged bindings are not rebuilt each
batch. Register synchronization uses native words rather than Python
integer lists. Execution can continue for up to 1,048,576 instructions per
batch while native services retain their original deadlines. MMIO capacity
and terminal flushing bound the larger batches without growing buffers.

Nine focused MAME checks passed. A current-change lifetime check verified
live register writes, pinned device storage, release on rebinding and view
lifetime after CPU destruction. A ten-second required-LAPM AT&T1 check at
24,000 bit/s echoed 3,995 exact bytes and escaped successfully. Python still
orchestrates host events and worker snapshot synchronization; this is not
a standalone executable or complete native ownership of every board object.


Milestone 14 complete: native timer control reads and delay grants.
All modeled timer reads now use the shared C++ implementation, including
calibrated delay acceleration and existing counters. MAME evaluates the
existing ROM transfer-range exclusion directly before granting a delay;
Python timer views call the same implementation. Board-clock selection
still propagates its DSP/line scheduling change through the host callback.

Three selected existing timer/MAME cases passed, including reference/native
register-and-clock scripts with acceleration enabled and disabled. A focused
current-change check matched granted and transfer-excluded control reads
without Python bus callbacks. A ten-second required-LAPM AT&T1 check at
24,000 bit/s echoed 4,042 exact bytes and escaped successfully.


Milestone 15 complete: native software interrupt and CPU exception entry.
The configured MAME runtime uses the existing MAME interrupt entry for
ordinary vectors. It builds FLAGS/CS/IP frames and handles interrupt flags
inside the CPU. Existing fault counts are folded by batch. Parameter-flash
host services and watched/guarded frames retain their existing boundary;
COURIER_NATIVE_INTERRUPTS=0 retains the previous software/fault path.

Focused current-change checks passed native INT/IRET, the stack/FLAGS frame,
fault accounting and explicit host/watched-frame fallback. Two selected
existing interrupt checks passed. A ten-second &M5 AT&T1 check at 24,000
bit/s echoed 3,995 exact bytes, escaped, and reported zero lost characters,
block errors, resends and timeouts.

Practical boundary remaining: DSP reset/NMI still owns Python loader,
runtime-bus and bridge lifecycle state alongside native core/media reset.
Moving just the pin callback would retain that dependency and split reset
ownership. Removing it requires migrating the board/DSP lifecycle as one
unit. Timer-0 clock identification also retains its host propagation callback
because it updates DSP and line scheduling together. These rare paths have
no demonstrated performance benefit from an isolated callback migration.
The native execution context is persistent, but complete board ownership
and a standalone native executable are not yet implemented.


Milestone 16 complete: native C51 loader and shared lifecycle state.
The standalone native bridge owns bootstrap storage, completion comparison,
loader startup/NMI settling and transfer acknowledgement loops in C++.
Loader, active/runtime and reset-related fields are live native state views;
core replacement updates the borrowed native core reference. Python retains
the existing host completion actions and, at this milestone, reset routing.

Three selected bridge checks passed construction, core replacement and
shared reset state. Fresh isolated firmware boot, AT commands and settings
queries passed with a matching DSP download. No probes or new debugging
interfaces were added. Work continues with native reset/media ownership
and direct P1 pin routing, as requested after the earlier boundary report.
